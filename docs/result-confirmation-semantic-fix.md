# Unchanged Result Confirmation: Semantic Snapshot Fix

## Reproduced Failure

The initial regression command was:

```sh
node --test server/src/server/lib/__tests__/resultSnapshot.test.js
```

It failed on unchanged 2–2 proposals with reordered JSON keys, including nested objects and native-array history. Real score/penalty/lifecycle changes remained rejected. The full submit/confirm fixture then exposed another cause: `appendHistory` pushed onto the fetched native JSON array, mutating the expected snapshot before the guarded update compared it with the unchanged stored history.

The former SQL guard also compared browser/JavaScript re-serialisations against TEXT columns byte-for-byte. These are locally reproduced representation/concurrency defects, not proof of the exact live request's cause. No authenticated live match read, result mutation, flag reset or wallet change was performed.

## Comparison Contract

- `resultSnapshotContract.json` names JSON, lifecycle and counter fields and an explicit bookkeeping-event allowlist shared with the frontend.
- Object keys are sorted recursively; JSON text/object representations and whitespace are equivalent. All array ordering is preserved. Actual history event reordering, new proposal/correction/dispute events, changed scores, penalty decisions, submitting side and lifecycle remain conflicts.
- Missing/null/blank submission TEXT represents an unsubmitted sheet; null history represents no events. Malformed/nonconforming stored JSON is explicitly blocked with `INVALID_RESULT_DATA`, without deleting it or exposing private contents.
- Only `reminder_sent`, `report_viewed` and `deadline_checked` history events are excluded from proposal identity. Unknown history events remain significant. Bookkeeping appended after review is retained when the next result event is written.
- Scalar state normalisation is deliberate. New clients supply submitting-side/counter fields. Original seven-field clients retain submission/history/lifecycle protection when those newer optional fields are absent.
- `updated_date`, stream URLs and presentation changes are not proposal tokens. Modal preflight and backend use the same semantic contract.

## SQL and Transaction Behaviour

Regular negotiation mutations now select the row `FOR UPDATE`, compare the reviewed proposal semantically, and bind the actual observed database representations to the guarded update. TEXT comparisons are binary/null-safe; JSON history retains `CAST(? AS JSON)`. Finalisation flags still block writes. No stale proposal is blindly refreshed and accepted.

Zero affected rows are distinguished from a genuine no-op, missing match, already processed result or database guard mismatch. Database errors are not relabelled as stale proposals. HTTP conflict context contains only guard/field names, not submissions or private proof URLs.

Confirmation sheets, their audit-history event and official result/stat rows commit in the existing finalisation transaction. Failed pre-finalisation work rolls back the sheet and result together. Correction acceptance and automatic timeout finalisation use the same atomic patch path. `appendHistory` copies native arrays instead of mutating the fetched snapshot. Corrected scores are selected relative to the actual original submitting side, including the existing away-side fallback window.

A server-generated, match-bound semantic review fingerprint is recorded in the existing final history event. A matching actor/action/proposal retry can return the completed result idempotently. A different proposal, penalty decision, actor or later substantive resolution is rejected. No new schema, entity, revision column or migration is required. Old completed results without a receipt are not assigned invented retry evidence.

Participant identity is checked before deadline settlement on the confirmation path. Expired deadlines can legitimately auto-confirm under existing policy; an old manual confirmation then needs review of that terminal result rather than confirming it again.

## Wagers and Other Side Effects

No wager economics or settlement SQL were changed. The existing locked wager service refunds each reserved stake for an ordinary draw, including 2–2. Confirmation retries use the official recorded result, never a guessed winner. Existing settlement status, transaction and ledger-key safeguards prevent duplicate refunds/payments. A controlled wager-ledger failure rolls back the wallet transaction and can recover on an identical confirmation retry without repeating career records or notifications.

Only the winning finalisation transaction applies the result. Matching retries skip report/stat/career application and confirmation inbox publication. Existing idempotent progression/settlement mechanisms remain unchanged. No draws, trophies or prizes were manually generated by this work.

The existing post-commit derived-career/news/progression architecture was not broadly rewritten. Recovery from arbitrary process termination halfway through those pre-existing post-commit operations is not a newly implemented general repair system. The targeted failure between confirmation and finalisation is atomic and covered by rollback/retry tests.

## User Recovery

Genuine conflicts keep report inputs until the user explicitly chooses **Refresh and review**. The action warns that unsent inputs will be replaced, fetches the same frozen match ID and displays the latest score/penalty decision before another confirmation. It never auto-accepts that replacement. Successful refresh clears obsolete errors; successful confirmation closes the modal and refreshes GameDay. Submission has an immediate in-flight lock in addition to disabled controls and server concurrency safeguards.
